## 重点产品

### Pi API beta与机器人基础模型

平台 · 预览 / 限定开放

让获准参与的机器人团队上传示范数据、启动模型微调并通过托管推理控制自有机器人，形成按实际失败继续收集数据的迭代流程。

目标用户：拥有机器人硬件、控制接口和任务数据的开发公司及研究团队。

AI作用：机器人策略模型结合视觉、语言及动作数据学习控制，API支持针对任务微调；研究提出跨任务组合能力，但不保证任意本体和环境即插即用。

使用与交付：当前为申请参与的beta服务，使用厂商管理训练与托管推理基础设施；硬件适配、数据采集及现场验证仍由项目团队完成。

收费形式：beta访问、计算与后续商业条款需官方确认，本轮未核公开标准价格，不把候补登记或研究权重发布当作免费生产服务。

产品边界：云端推理存在网络与延迟依赖，官方也指出早期部署的连接挑战；研究演示和开放代码权重的范围不能外推为最新全部能力开放或物理安全保证。

分析围绕Pi API beta帮助机器人团队适配策略模型的工作流，并以公开研究解释技术方向；不评价合作方整机交付，不把实验性代码权重和托管API混为同一种开放范围，也不推断所有任务已达到生产可靠性。

> 以公开一手资料开展案头研究，围绕列明的重点产品与工作流分析。官方能力与研究判断分开；没有实际注册、付费调用、性能测试、用户访谈或销量审计。未披露的收入、成本、模型依赖和运营结果不编造。

## 需求与市场

### 机器人团队重复建设学习基础设施 · 研究判断

开发者不仅要做硬件，还要准备训练、数据和推理系统，重复工作可能阻碍具体应用。Pi API的需求是降低模型适配基础设施负担，但价值应看是否让团队更快获得可验证行为，而不是仅简化一次接口调用。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

### 通用模型仍需具体任务反馈 · 研究判断

不同机器人面对的物体、工具和环境差异很大，基础模型需要在项目中验证。研究应观察失败是否帮助决定下一批数据，而不能把通用模型名称理解为无需示范、调试或任务边界，实际应用仍需要完整团队。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>) · [π0.7研究说明](<https://www.pi.website/blog/pi07>)

## 目标用户

### 拥有硬件和数据的开发者 · 研究判断

主要用户需要可运行机器人、控制接口和示范采集能力，普通消费者不具备相同条件。目录应把API服务与家用机器人成品分开，不能因为研究视频包含家务就暗示公众购买模型即可获得可靠家庭助手。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

### 研究人员与商业集成者 · 研究判断

研究团队可能关注泛化实验，商业团队更关注稳定运行和维护，两者验收标准不同。beta反馈应分别记录科学探索与现场部署需求，不能用论文任务表现替代商业场景的连续运行和异常处理要求。

依据：[π0.7研究说明](<https://www.pi.website/blog/pi07>) · [Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

## 产品与工作流

### 上传微调部署的迭代链 · 研究判断

官方API流程包括上传任务数据、托管微调和推理，再用评估决定新数据。合理工作流需要保留数据版本、机器人配置和模型版本，避免结果变化后无法判断来自硬件、样本还是模型更新。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

### 现场失败需要回到数据设计 · 研究判断

机器人抓取失败可能与视角、物体或控制有关，不一定只需增加同类示范。研究应检查开发者如何归类失败、修改采集和重新验证，不能把API可训练当作会自动找到正确改进方向，更不应只保留成功片段。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>) · [openpi代码权重发布说明](<https://www.pi.website/blog/openpi>)

## AI技术与依赖

### 多模态条件帮助动作学习 · 研究判断

π0.7研究讨论语言、视觉目标和其他条件如何支持动作及技能组合，说明任务表达不限于文字。技术评价应控制训练与测试差异，检查新场景中的真实泛化，不能把研究中的初步组合能力描述为任意任务已经解决。

依据：[π0.7研究说明](<https://www.pi.website/blog/pi07>)

### 云端推理有物理时间约束 · 研究判断

API提供托管推理，机器人动作却发生在现场，网络连接和时序可能影响行为。官方承认早期项目有连接挑战，部署评估应检查失联和延迟时如何停止或降级，不能把普通云API的可用性直接当作机器人控制可靠性。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

## 竞争与替代

### 与自建策略和专用控制比较 · 研究判断

开发团队可以训练专用模型或采用传统控制，基础模型服务需要证明减少了适配工作而保留可靠性。比较应固定机器人和任务条件，记录数据采集、调试及维护投入，不宜只比较模型演示成功率。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>) · [π0.7研究说明](<https://www.pi.website/blog/pi07>)

### 开放研究包与托管服务不同 · 研究判断

openpi提供实验代码和权重，Pi API则管理训练与推理，两者的自由度、资源和支持不同。用户应明确需要的是研究控制权还是托管便利，不能把开放发布等同最新API全免费，也不应将所有组件笼统称为完全开源。

依据：[openpi代码权重发布说明](<https://www.pi.website/blog/openpi>) · [Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

## 商业模式

### 候补申请不代表标准采购 · 研究判断

当前API为beta并通过申请选择参与，公开页面没有适用于所有项目的价格与服务承诺。商业评估应先确认访问、数据和支持条件，不能把登记成功视为已获得生产许可或预计交付，也不猜测按机器人收费的具体方式。

依据：[Physical Intelligence当前官网与候补入口](<https://www.pi.website/>) · [Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

### 节省模型准备不等于省去集成 · 研究判断

即使托管基础设施减少了部分工作，硬件适配、采集和现场安全验证仍由项目承担。应按完整应用周期计算投入，而不是只比较训练接口速度；本研究没有商业账单或部署数据，不推算单位机器人的盈利。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

## 体验与交付

### 让开发者看见版本和反馈 · 研究判断

模型更新可能改善部分任务也影响已有行为，API体验需要清楚版本、训练状态和评估结果。研究应测试回退、重复训练和失败诊断，确保团队能够解释变化，而不是只获得一个无法追踪的最新模型端点。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)

### 研究说明应帮助判断适配性 · 研究判断

公开发布明确某些模型未必适合每个机器人，这种边界对开发者很重要。体验评价应看文档是否支持检查硬件和数据条件，避免团队依据家务视频过度预期；能快速发现不适合也有实际价值。

依据：[openpi代码权重发布说明](<https://www.pi.website/blog/openpi>)

## 风险与机会

### 物理执行不能只靠模型信心 · 研究判断

策略模型输出动作会产生现实后果，部署者需要独立的运行限制、停止与接手机制。研究机会在减少适配成本并提高可验证性，不能把通用模型能力或云服务成功响应当作物体操作安全的充分证据。

依据：[Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>) · [π0.7研究说明](<https://www.pi.website/blog/pi07>)

### 早期应用与广泛开放保持区分 · 研究判断

合作案例展示了可能性，但样本和场景有限，不能推断任意机器人都可用。目录保留beta、候补和实验发布边界，后续应关注独立重复与长期运行，不能由论文或伙伴数量预测商业成功率。

依据：[Physical Intelligence当前官网与候补入口](<https://www.pi.website/>) · [Pi API beta发布与限制](<https://www.pi.website/blog/api-beta>)
